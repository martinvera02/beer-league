🏗️ Arquitectura general
Frontend SPA (Single Page Application) desplegada en Vercel. El backend es completamente Supabase: PostgreSQL para datos, Auth para usuarios, Storage para imágenes, y Realtime para el chat y votos en vivo. No hay servidor propio — toda la lógica de negocio vive en funciones SQL de Supabase (PostgreSQL functions) protegidas por Row Level Security (RLS).

🔒 Row Level Security (RLS)
Todas las tablas tienen RLS habilitado. Los usuarios solo pueden leer y escribir sus propios datos, excepto en casos específicos como ver el ranking de su liga. La lógica sensible (comprar powerups, abrir préstamos, resolver guerras) vive en funciones SQL con security definer para ejecutarse con privilegios elevados.
03 — Features principales

Módulos de la app

Beer League está organizada en módulos independientes accesibles desde la barra de navegación inferior.

🏆 Ligas & Ranking

Sistema de ligas y competición

El núcleo de la app. Cada usuario puede pertenecer a múltiples ligas cerradas. Dentro de cada liga hay un ranking de puntos en tiempo real que se resetea cada 10 días (temporada). Al final de temporada el top 3 recibe monedas.

Crear o unirse
El owner crea la liga y obtiene un código único (BEER-XXXX-XXXX). Los demás se unen con ese código.
Anotar consumiciones
Cada consumición suma puntos según el tipo de bebida y el multiplicador del mercado. Se anota en todas las ligas del usuario a la vez.
Fin de temporada
Cada 10 días se ejecuta automáticamente end_season_and_reward() via GitHub Actions. Reparte monedas al top 3 y guarda el historial.

📈 Mercado

Cotización de bebidas

Cada bebida tiene un precio en el mercado que varía entre x0.5 y x2.0. El multiplicador afecta directamente a los puntos y monedas obtenidos al anotar. El mercado se actualiza cada hora.

Fluctuación automática
Cada hora un job de GitHub Actions llama a update_drink_market() que ajusta los precios con variación aleatoria.
Operaciones LONG/SHORT
Los usuarios pueden apostar monedas a que el precio subirá (LONG) o bajará (SHORT). Máximo 3 operaciones por día. Solo disponible de 22:00 a 02:00h.

⚖️ El Juzgado

Votación de consumiciones sospechosas

Cualquier miembro puede impugnar una consumición de las últimas 24 horas. Se abre automáticamente un juicio donde la liga vota en tiempo real vía Supabase Realtime.

Impugnación
El acusador pulsa "Impugnar". El juicio se abre para toda la liga automáticamente y el acusado recibe una notificación push.
Votación en vivo
Los miembros votan ✅ Real o ❌ Falso. Los votos se ven en tiempo real con barras animadas. El acusado puede subir una foto como prueba.
Veredicto automático
Si ≥65% vota FALSO → consumición anulada (0 puntos). Si ≥65% vota REAL → consumición validada. La función resolve_dispute_by_votes() lo gestiona todo.

05 — Lógica de negocio

Funciones SQL clave

Toda la lógica crítica vive en funciones PostgreSQL con security definer. El frontend solo llama a supabase.rpc().

Función Qué hace Cuándo se llama
add_drink_with_effects()Anota consumición aplicando powerups activos (freeze, double, turbo, gamble, invisible). Inserta en todas las ligas del usuario en una sola transacción.Al pulsar "Anotar" en AddDrink
end_season_and_reward()Cierra la temporada activa, reparte monedas al top 3 de cada liga, guarda en season_results y abre una nueva temporada.GitHub Action cada 10 días
update_drink_market()Ajusta precios de todas las bebidas con variación aleatoria respetando los límites x0.5–x2.0.GitHub Action cada hora
buy_powerup()Valida saldo, aplica el powerup, descuenta monedas y registra el efecto activo. Gestiona el cooldown de 30min.Al comprar en la Tienda
resolve_dispute_by_votes()Calcula porcentaje de votos fake. Si ≥65% → anula consumición (0 pts) y notifica al acusado.Tras cada voto en El Juzgado
update_war_battle_progress()Recalcula challenger_current y defender_current para todas las batallas activas. Detecta completado y asigna winner_league_id.Al cargar ClanWar
resolve_clan_war()Cuenta batallas ganadas por equipo, determina ganador, reparte reward_coins a los miembros del equipo vencedor.Al expirar la guerra
get_war_captain()Devuelve el user_id con más puntos en la temporada activa para una liga dada.Al declarar o aceptar una guerra
claim_daily_reward()Gestiona la racha de recompensa diaria. Día 7 da powerup gratis. Actualiza streak y añade monedas.Al abrir cofre en Home
request_bank_loan()Valida que no haya préstamo activo, calcula límite (2× saldo), acredita monedas y crea el registro de deuda.Al pedir préstamo en Banco
join_league_by_code()Busca liga por código (case-insensitive), comprueba que no sea ya miembro, inserta en league_members.Al unirse con código
send_coins_to_member()Transfiere monedas entre usuarios dentro de una liga. Registra en league_transfers.Al enviar en Transferencias

Flujo de una consumición

// Frontend → AddDrink.jsx const { data } = await supabase.rpc('add_drink_with_effects', { p_drink_type_id: 2, // cerveza p_season_id: seasonId, p_league_ids: [14, 18], // todas las ligas del usuario p_drink_group_id: uuid(), // agrupa inserts de varias ligas }) // La función SQL: // 1. Comprueba si el usuario está congelado (freeze) // 2. Obtiene multiplicador del mercado para la bebida // 3. Aplica double_points si está activo // 4. Aplica turbo si está activo para esa bebida // 5. Aplica gamble (x0 o x4 aleatorio) // 6. Aplica invisible (muestra 0 pts pero guarda real) // 7. Inserta en drinks por cada league_id // 8. Actualiza wallet (+coins = puntos × 10) // 9. Gestiona deuda si balance < 0 // Retorna: { success, final_points, coins, ... }
06 — Automatización

GitHub Actions

Las tareas automáticas corren en GitHub Actions y llaman directamente a la API de Supabase. No hay servidor backend.

⏰
Actualización de mercado
Llama a update_drink_market() cada hora en punto. Ajusta los precios de todas las bebidas con variación aleatoria controlada.
Cron: 0 * * * *
🏁
Fin de temporada
Ejecuta end_season_and_reward() cada 10 días. Cierra la temporada, reparte monedas al top 3 de cada liga y abre una nueva.
Cron: 0 0 */10 * *
🍖
Operación Barbacoa
Notificación masiva el 8 de mayo a las 22:00 UTC (medianoche Madrid). Llama a notify_operacion_barbacoa() para avisar a todos los usuarios del evento.
Cron: 0 22 8 5 *
